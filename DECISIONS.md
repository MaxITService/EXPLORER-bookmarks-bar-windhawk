## Layout decisions

- **0.4.4–0.4.7:** Measurements found Explorer's `[Auto, *, *]` header gave half the added height to the command row and clipped the bookmark strip. Version 0.4.5 changed that row to `Auto` and reserved 44 host units at 96 DPI; 0.4.6 centered 32-unit buttons with 3-unit top/bottom margins; 0.4.7 lifted the ScrollViewer by 3 units to balance visible gaps. Exact measurements are in [the layout record](diagnostics/layout.md).
- **Two-row layout:** Double Decker uses 38/40-unit rows, a 2-unit lower inset, 84 host units at 96 DPI, and an `Auto` command row. Its lower row has separate `folders2` storage and backup JSON, with no FX.
- **Adaptive layout:** The production source wraps one bookmark list into 1–4 rows and reserves `40*N + 4` host units at 96 DPI; overflow after row four pans horizontally. The user verified three-row geometry and accepted an intermittent background shade difference.

- **0.8.0 candidate:** Adds optional recent folders, off by default. The bar is now a two-column Grid: the scrolling bookmark strip, then a first-row recents column with a `|` separator, 1–3 recent buttons (newest nearest the edge) and an RC button at the right edge. Recent buttons fold into RC when showing them would add a bookmark row; without RC the oldest are hidden first, and RC is forced on while no recent button exists. The RC menu lists remembered folders without a button (at most 10 in total with the buttons) and switches the source between File Explorer history and Windows recent items. Explorer history comes from `DWebBrowserEvents2` navigation events on each UI thread's own tabs, found through `ShellWindows` events, and is stored in local storage (64 entries, so bookmarks and missing folders can be filtered out). Windows recent items are folder shortcuts in the Recent folder, identified by their stored attributes without probing targets; Start's recent-files setting and the `NoRecentDocsHistory` policy are reported in the RC menu. Clearing or removing Windows items only hides them in mod storage until Windows records a newer use. Middle-click removes a recent folder, a drag onto the strip inserts it as a bookmark, and bookmarked folders are never listed. Right-click RC shows **Clear recent folders**, or clears at once when that setting is on. Local x64 and ARM64 checks pass; the build has not been tested in Explorer.
- **0.8.1 candidate:** Ctrl+B toggles a bookmark for the active tab's folder (setting on by default). A `WH_GETMESSAGE` hook on each Explorer UI thread swallows the key before Explorer dispatches it and defers the work to the same thread timer as recent-folder updates. Explorer has no Ctrl+B shortcut. The key is left alone while a Win32 edit control (rename) or a XAML text box in that frame's island (address bar, search) has focus, and on auto-repeat. The personal build carries the same change as 0.8.1. Untested in Explorer.
- **0.8.2 candidate:** Right-clicking a bookmark or recent-folder button opens it in a new Explorer window through the Folder verb `opennewwindow`, the command behind Explorer's **Open in new window**. The handler uses `ContextRequested`, so the context-menu key and touch press-and-hold do the same. FX and RC menu entries are unchanged. The personal build carries the same change as 0.8.2. Untested in Explorer.
- **0.8.3 candidate:** When the file list (`DirectUIHWND`) has focus, Ctrl+B uses the active tab's selected filesystem folders (`IFolderView::Items(SVGIO_SELECTION)`, excluding `SFGAO_STREAM` items such as ZIP files): it removes them when all are bookmarked and otherwise appends the missing ones. Without a folder selection it toggles the current folder as before. Folders dragged from File Explorer or another program onto the bar are inserted at the marked position, or appended over the recents. The drop accepts only Link or Copy, never Move, so the source never deletes what it believes was moved. Items arrive through `GetStorageItemsAsync`; unloading waits for that operation, and the completion posts a registered message to the frame that the thread's `WH_GETMESSAGE` hook turns into a bar refresh. The bar root has a transparent background so its empty parts accept drops. At the user's request, one Ctrl+B or drop handles at most 20 folders. The personal build carries the same change as 0.8.3. Untested in Explorer; whether Explorer's XAML island receives OLE drops from its own file list is unverified.
- **0.8.4 candidate:** The user reported that 0.8.3 showed the **Add to bookmarks** drag caption (so the XAML island does receive OLE drags from the file list) but froze the Explorer window on drop; the window kept pumping messages (`IsHungAppWindow` false) and a full dump was saved as `%TEMP%\explorer-drop-freeze.dmp`. The file list starts the drag on the same UI thread. The likely cause is the drop deferral: XAML waited for it inside the drop while `GetStorageItemsAsync` needed that thread. 0.8.4 takes no deferral; the read completes after the drop returns and posts the refresh message as before. Drops pending a read are counted, and unloading waits for them for at most 5 seconds instead of indefinitely. The personal build carries the same fix. The dump has not been analyzed, since no debugger is installed.

It follows Ctrl+B, a drop, the **+** button and a recent folder dragged onto the strip; removals and successful adds stay silent. It is a popup, so the confirmed bar layout is untouched. - **0.8.7 candidate:** Robustness and review fixes for the 0.8.x code, with no new features, prepared for another review by the Windhawk AI reviewer of the ramensoftware/windhawk-mods submission (nothing was pushed or commented there). (1) `GuardHandler` wraps the lambda of every XAML delegate (`Track*` helpers, the six bar-root handlers, the command bar `Loaded`/`Unloaded`) in `try/catch`, so an exception is logged instead of reaching XAML as a failed HRESULT; `RefreshPanel` catches its own exceptions and resets its folder-check stamp so a half-built panel is rebuilt on the next hover. The drop counter is decremented again when registering the read completion throws. (2) To find the folders in the selection, Ctrl+B checks at most `kMaxSelectionScanned` (1000) selected items, skipping files and ZIP archives, which bounds the work after Ctrl+A in a huge folder; with no folder among them Ctrl+B still toggles the current folder. Folders after the first 1000 selected items are not seen. (3) A backup with a UTF-8 byte order mark loads. (4) `SamePath` uses `CompareStringOrdinal`, so Cyrillic and other non-ASCII path case differences count as the same path (stored duplicates are not migrated; importing such duplicates is now rejected). (5) Ctrl+B acts only in a window whose bar is installed, so it is no longer swallowed where the bar could not be inserted (unknown Windows build). (6) Windows recent items are read only when the Recent folder is on a local fixed drive; a scan reads at most 128 links (was 256) and stops at 32 folders (was 64), and logs its link count, folder count and duration; the 5-second cache is unchanged. (7) `g_bars` is `[[clang::no_destroy]] thread_local std::optional<std::list<BarState>>` as the Windhawk wiki asks for containers of XAML references, released explicitly by `RemoveBarVisuals` and `g_bars.reset()` in `CleanupCurrentThread`, which returns early when an earlier window on the same thread already ran it. (8) `recentButtons` and `recentHistory` declare `$min`/`$max`, written with the `#! ` marker because Windhawk 1.7.3, the installed release, refuses a settings block with unmarked `$min`; the range is a hint only, so `LoadRecentSettings` still clamps. (9) `ReadFxSetting` no longer null-checks `Wh_GetStringSetting`; `#include <memory>` added; `Wh_ModUninit` logs drops still pending after its 5-second wait. README and setting text state that Windows recent items come only from a local Recent folder. Known limitation, left unchanged without an Explorer test: closing a window does not clear its `RecentTracker`, so the `ShellWindows` listener stays registered and the thread ends without cleanup (commented in the code). New breadcrumbs: `Selection: …`, `Windows recent scan: …`, `Ctrl+B ignored: no bookmarks bar in this window`, `… handler failed: …`, `Bookmarks bar refresh failed: …`. Local x64 and ARM64 checks pass with no warnings and the PR validator reports none; untested in Explorer.

Local x64 and ARM64 checks pass with no warnings; untested in Explorer.
- **0.8.9 candidate:** Two fixes from a static review of 0.8.8. (1) `KnownFolderPath` passes `KF_FLAG_DONT_VERIFY`: without it Windows checks that the folder exists, which can stall the UI thread while a new window builds its bar when Desktop, Documents or Downloads are redirected to an unreachable share, and drops that entry from FX; the Recent folder lookup had the same check before its own `CheckFolderStatus`. The standard FX entries now pass `CheckFolderStatus` like the custom ones, so a standard folder missing from a local fixed drive stays hidden (logged as `FX: … hidden, missing from a local disk`) and a redirected share is listed unchecked, as the 0.7.8 entry states. (2) Import copies each JSON string with its full length. `Windows.Data.Json` turns a `\u0000` escape into an embedded NUL (checked locally), and `c_str()` cut the path there, so `"C:\\Windows\u0000junk"` loaded as `C:\Windows`; the control-character check now rejects the file, logged as `Bookmark backup rejected: …`. Not taken, at the user's decision: a drop read still pending after the 5-second unload wait can call unloaded code (it needs a read slower than 5 seconds during an unload, which every settings save causes since the mod has no `Wh_ModSettingsChanged`; the existing `Wh_ModUninit: … still pending` line reports it); `KillTimer` leaving timer messages behind was rejected, since `WM_TIMER` is generated only for live timers, `DispatchMessage` checks the callback against the process's live timers, and cleanup runs on each UI thread between messages; synchronous `SHGetFileInfoW` for existing local folders was skipped, since it stalls only when a `desktop.ini` icon points to an unreachable share and is not in Windows' icon cache, and an asynchronous loader would add work that unloading must wait for. Local x64 and ARM64 checks pass with no warnings; untested in Explorer.
- **0.8.10 candidate:** At the user's request, the recent-folder settings form one **Recent folders** group, because Windhawk cannot hide or disable a setting that depends on another, and the flat list made **RC button** look independent of the switch that turns off recent folders and RC together. The group holds **Show recent folders** (`recent.enabled`), **Buttons** (`recent.buttons`), **Remembered folders** (`recent.history`) and **RC button** (`recent.rcButton`), a list that replaces the two RC toggles: `menu` (shown, right-click offers Clear, the default), `clear` (shown, right-click clears at once) and `hidden`; an unknown value behaves like `menu`. The switch's text states that the other settings apply only while it is on. The old keys (`recentFolders`, `recentButtons`, `recentMenuButton`, `recentHistory`, `recentRightClickClears`) are no longer read, so an installed 0.8.x falls back to the defaults once, with recent folders off; the catalog submission is 0.7.8 and never had them. The remembered folders in local storage are unaffected. `LoadRecentSettings` logs `Recent folders: on|off, N button(s), N remembered, RC <mode>`. Bar behavior is unchanged. Local x64 and ARM64 checks pass with no warnings; untested in Explorer.
- **Personal build 0.8.0:** At the user's request, `explorer-folder-bookmarks-bar-personal.wh.cpp` is production 0.8.0 with `@include *` and a **Recent folders in file dialogs** setting (off by default). It hooks `CoCreateInstance` and `CoCreateInstanceEx` in `combase.dll`; each new `CLSID_FileOpenDialog` or `CLSID_FileSaveDialog` receives the listed recent folders through `IFileDialog::AddPlace(FDAP_TOP)`. Local fixed folders are parsed normally; other paths use `SHSimpleIDListFromPath` so the dialog never waits on network or removable storage. The Explorer bar code runs only in `explorer.exe`. Dialogs that do not come from COM creation (for example Store app pickers) are unchanged. The order of several top places and legacy `GetOpenFileName` coverage are unverified.
- **Personal build frozen:** At the user's request, the personal build stays at 0.8.5 and receives no further changes, including production ports. Reason: `@include *` loads the mod into every process, and the `CoCreateInstance` hook in each of them may look suspicious to anti-cheat software; turning the setting off does not help, since the DLL is already loaded. The dialog cannot be watched from another process: `CLSID_FileOpenDialog` and `CLSID_FileSaveDialog` are `InProcServer32` entries for `comdlg32.dll` with no local server or broker, and `AddPlace` must run inside the dialog's process before it is shown. Windhawk selects target processes by name, not by behavior. The options that were weighed and left undecided: an explicit `@include` list of programs, dropping the dialog feature, or lifting the freeze later. COM hijacking through `HKCU` and pinning recents to Quick Access were rejected. Production and Double Decker are limited to `explorer.exe` and contain no such hook.
- **Double Decker frozen:** At the user's request, `explorer-folder-bookmarks-bar-double.wh.cpp` stays at 0.7.8 and receives no further changes, including production ports and the 0.8.x features, until the user lifts the freeze. It remains untested in Explorer. Only production is developed and checked.
- **Drive menu:** Right-click FX enumerates logical drives on every open. It omits only roots that `CheckFolderStatus` reports missing; network, removable and optical drives are listed unchecked with a type label.
- **Backup:** Save/Load uses file dialogs, with the former profile filenames suggested by default.
- **Architecture:** Both sources declare `x86-64`. Windhawk uses x64 on x64 Windows and ARM64 for `explorer.exe` on Windows ARM64. Local compilation checks cover both targets; live Explorer behavior on ARM64 has not been verified.
