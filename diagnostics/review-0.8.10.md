# Static reliability review of 0.8.10 (2026-09-29)

Scope: `mods/explorer-folder-bookmarks-bar.wh.cpp`, compared with the official [Explorer Command Bar](https://github.com/ramensoftware/windhawk-mods/blob/main/mods/explorer-command-bar.wh.cpp), [Taskbar Folder Menus](https://github.com/ramensoftware/windhawk-mods/blob/main/mods/taskbar-folder-menus.wh.cpp), and the Windhawk [global-object shutdown guide](https://github.com/ramensoftware/windhawk/wiki/Global-objects-and-process-shutdown). This is code review only; 0.8.10 has not been tested in File Explorer. No source changes were made for this review.

## Findings, in priority order

1. **Drop completion can outlive the mod DLL.** `OnBarDrop` registers a WinRT `GetStorageItemsAsync` completion implemented in this DLL (lines 3668–3716). `Wh_ModUninit` waits up to five seconds, logs if reads remain, then returns anyway (lines 4438–4445). A later completion would execute unloaded code. The Explorer Command Bar mod deliberately waits without a timeout for its own worker threads before unload, and logs what holds the wait ([source](https://raw.githubusercontent.com/ramensoftware/windhawk-mods/refs/heads/main/mods/explorer-command-bar.wh.cpp)). Recommended change: retain cancellable async operations, cancel pending reads on unload, then ensure every completion has finished before the DLL can unload. Keep a diagnostic log for slow cancellation. Test by dropping folders from a slow provider and disabling or saving mod settings while the read is pending. Avoid reintroducing a drop deferral: 0.8.3 froze Explorer that way.
2. **Recent tracking lacks a guaranteed last-window teardown path.** `g_recentTracker` is a raw `thread_local` pointer intentionally destroyed only by `StopRecentTracking` (lines 3177–3246). `CleanupCurrentThread` calls that function, but `Wh_ModUninit` reaches only threads that still have Explorer windows (lines 4284–4292 and 4445). When the last window on a UI thread closes, `CommandBar.Unloaded` removes bar visuals but does not stop recent tracking (lines 4072–4104); no subsequent sync is guaranteed. This can leave the tracker, COM references, and event sink registered. A sink left registered during mod unload would be especially risky; whether COM disconnects it automatically as the thread exits needs a live test. Recommended change: trigger a final UI-thread cleanup when the last bar/window goes away, unadvise all connection points there, and release the XAML state on that thread. The [Windhawk shutdown guide](https://github.com/ramensoftware/windhawk/wiki/Global-objects-and-process-shutdown) requires explicit cleanup of thread-affine objects on the owning thread.
3. **Settings changes reload the mod.** 0.8.10 has no `Wh_ModSettingsChanged`, so even an FX label edit can enter the full unload path above. [Explorer Command Bar](https://raw.githubusercontent.com/ramensoftware/windhawk-mods/refs/heads/main/mods/explorer-command-bar.wh.cpp) reloads settings and refreshes each UI thread in `Wh_ModSettingsChanged`; [Taskbar Folder Menus](https://github.com/ramensoftware/windhawk-mods/blob/main/mods/taskbar-folder-menus.wh.cpp) uses the same broad approach. This is a worthwhile follow-up after the drop and tracker lifetimes are safe. It needs handling for recent-tracking enable/disable and the Ctrl+B hook, not just a panel redraw.

## Existing good practices

- The production source already hooks `kernelbase!LoadLibraryExW`, scans existing windows, tracks XAML handlers, and guards the bar's UI-thread state. These are the same broad stability patterns used by Explorer Command Bar.
- `g_bars` uses `[[clang::no_destroy]]` and explicit UI-thread cleanup, consistent with the Windhawk shutdown guide. The remaining gap is reaching a thread after its last window closes.
- Folder-status checks avoid probing network and removable storage from the Explorer UI thread.

Next step: fix items 1 and 2 in a new development version, compile locally, then test enable/disable, settings save, slow drops, closing the last Explorer window, and Explorer restart. A passing local compile does not establish runtime safety.
